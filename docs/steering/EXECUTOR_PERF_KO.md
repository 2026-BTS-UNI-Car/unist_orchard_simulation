## 2. 바뀐 것

### 2.1 틱 전에 조향 상태 새로 읽기 (`executor_main._refresh_steering`)

- 조향 상태는 구동 응답마다 함께 온다(send_hz 10 Hz).
- 한 걸음(`step`)의 입력 처리가 길면 그 걸음의 틱은 지난 구동 응답만 본다. 예: 빽빽한 스캔의 통로 갱신이나 재획득.
- 조건은 넷 다 맞을 때다:
  - front_steer MOTOR 이고, run 이 ACTIVE 이고, 클라이언트가 ARMED 다.
  - 걸음이 시작할 때 상태 나이가 `steer_status_max_age_s`의 절반(0.15 s) 이하였다.
  - 입력 처리 뒤에는 그보다 낡았다.
  - 이때 틱 전에 브리지 `status`를 한 번 읽어 넣는다.
- 읽은 상태에는 MCU 상태 줄의 나이(`age_ms`)가 들어 있다. 그래서 다음 경우는 전과 같이 `steering_feedback_stale`로 끝난다:
  - MCU 상태 줄이 늦거나 끊긴 경우
  - 브리지가 멈추거나 답하지 않는 경우(넣을 것이 없다)
- 걸음이 이미 늦게 시작하면 새로 읽지 않는다. 예: 실행기 멈춤, 루프 정지.
  - 실행기 자신의 늦음은 0.3 s 규칙과 stall guard(0.35 s)가 그대로 지킨다.
  - 첫 회귀에서는 이 조건이 없었다. 그래서 T1 대본 8개에서 실행기 멈춤 뒤에도 새로 읽어 기록이 달라졌고, 조건을 좁혔다(26d69e0).
- status 요청은 lease 를 쓰지 않고, 움직임을 보내지 않고, 래치를 걸지 않는다.
  - 셈 `steer_refreshes`, `steer_refresh_failures`는 쓰일 때만 생긴다.
- 빠른 SIM 에서는 입력 처리에 SIM 시간이 흐르지 않으므로 이 요청이 생기지 않는다. 빠른 SIM 틱의 조향 상태 나이는 최대 0.120 s 였다(nominal, W2, curve_l30).
- G-SIM F 기록(세 run)을 읽어 본 것. 분석이며 Gazebo 로 확인하지는 않았다:
  - ACTIVE 틱 2,648 개 가운데 기록된 상태 나이가 0.15 s 를 넘은 틱은 87 개(3.3 %)였다.
  - 틱 간격은 최대 0.325 s 로 stall guard 를 넘지 않았다.
  - 세 끝 모두 그 걸음의 스캔 처리 뒤 나이가 0.3 s 를 넘은 경우다. 새로 읽었다면 나이는 MCU 줄 나이(0.05 s 안팎)였을 것이다.
- 시험(`tools/row_executor/tests/test_steer_refresh.py`):
  - 0.25 s 처리가 있어도 상태를 한 번 읽고 계속 간다.
  - 새로 읽기가 없으면 stale 로 끝난다.
  - MCU 줄이 0.4 s 낡았으면 stale 로 끝난다.
  - 답하지 않는 브리지면 stale 로 끝난다.
  - 늦게 시작한 걸음은 새로 읽지 않고 stale 로 끝난다.
  - 0.35 s 를 넘는 처리는 stall_guard 로 멈춘다.
  - 한도 0.3 s 는 그대로다.

### 2.2 시작한 프로세스의 객체를 GC 밖으로 (`executor_main.freeze_startup_objects`)

- 루프 시작 바로 앞에서 전체 GC 를 한 번 하고 `gc.freeze()`를 한다. 사건 `gc_freeze`를 남긴다.
  - 넣은 곳: `executor_main.main`(Jetson), `steering.exec_container_main`(SIM 스택).
- 실행기 같은 프로세스에서 잰 전체 GC(`gc_pause.py`, 3 번씩, 한 번에 5 회):
  - 대상 프로세스: 실행기 패키지, numpy, scipy, SHADOW front_steer 루프 600 걸음. 추적 객체 약 48,000 개.

  | 코어 | freeze 전 [ms] | freeze 뒤 [ms] |
  |---|---|---|
  | P | 20.5~29.9 | 0.00~0.01 |
  | 저전력 E | 31.9~33.5 | 0.00~0.01 |

  - rclpy 는 이 PC 에 없어 넣지 못했다. 실제 프로세스는 객체가 더 많다.
- 루프가 계산하는 값은 바뀌지 않는다. 빠른 SIM 은 `main`을 거치지 않는다.

### 3.4 ARM(Jetson Orin Nano) 추정 — 재지 않음

- 가정: 파이썬·numpy 단일 스레드에서 Cortex-A78AE 1.5~1.7 GHz 가 이 PC 의 P 코어보다 3~4 배 느리다. 일반적인 비율이지 잰 값이 아니다.
- 추정 결과:

  | 항목 | 추정 |
  |---|---|
  | 스캔 처리 평균 | 약 60~90 ms/스캔(3.1 의 P 코어 평균 21~23 ms × 3~4) |
  | 통로 갱신 스캔 | 150~200 ms |
  | 재획득 스캔 | 300~400 ms |
  | 전체 GC(freeze 없을 때) | 약 80~120 ms |

- 스캔 주기 0.1 s 에 견주면 실행기는 스캔을 다 처리하지 못하고 최신 것만 처리한다. 통로 갱신마다 틱이 늦는다. 2.1 의 새로 읽기와 2.2 의 freeze 는 이 늦음이 멈춤으로 이어지는 것을 막지만, 처리량 자체는 줄이지 않는다.
- 실제 값은 Jetson 에서 재생으로 재야 한다(사용자 현장 일). 실행기 패키지만 있는 사본에서 `row_shadow_replay.py`가 기록마다 `on_scan_ms_p50_p90_p99_max`를 낸다(`REPLAY_BASELINE_KO.md`).

## 5. 남은 일과 제안(결정 필요, 출력이 바뀜)

1. 통로 탐색 헤딩 범위
   - 지금: 통로 추적 중에도 ±90°를 2° 간격(90 헤딩)으로 본다.
   - 제안: 추적 중에는 추적 헤딩 둘레 ±20°(약 20 헤딩)만 보고, 모호함 검사를 위해 N 번마다 전체를 본다. `observe_scan_corridor`가 약 3~4 배 빨라질 것으로 본다(추정).
   - 모호함 판정이 바뀌므로 사전등록 개정과 넓은 평가를 다시 해야 한다.
2. 재획득 축 탐색(`_acquire`, 축마다 `_axis_pair`): 축 수를 줄이거나 굵게 본 뒤 세밀하게 본다.
3. ICP 반복 수와 점 수. 정확도 영향은 10/10 재생과 넓은 평가로 본다.
4. 스캔 처리를 루프 밖 일꾼으로 옮기기
   - 결정 시점이 바뀌어 빠른 SIM 결정성이 깨지므로 설계 결정이 필요하다.
   - 2.1 의 새로 읽기가 있으면 0.35 s 안의 늦음은 멈춤 없이 지나간다.
5. Jetson 에서 실제 시간 재기(3.4).
6. Gazebo(G-SIM)에서 로컬 도구로 다시 확인: 새 이미지에 2.1~2.3 이 들어가야 한다. 다음 단계의 몫이다.
