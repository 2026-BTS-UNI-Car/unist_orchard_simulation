# 단일 열 추종 G-SIM 확인 사전등록 (steer_follow_gsim_v1)

- 작성: 2026-11-12. 등록 번호 `steer_follow_gsim_v1`. 기계가 읽는 사본: `PREREG_STEER_FOLLOW_GSIM.json`(`steering.gsim_follow.prereg()`의 출력과 같아야 한다. 시험 `sim/ubts/test_steering_gsim_follow.py`가 본다).
- 대상: 열 추종 제어기 `sim/ubts/closed_loop/steer_control.py`(실행기 제어기 자리의 `{"kind": "row_follow"}`, 기본값 그대로)를 Docker 스택(G-SIM, Gazebo)의 실행기 컨테이너에서 돌린 것.
- 앞 등록: `PREREG_STEER_FOLLOW_KO.md`(`steer_follow_v1`, 빠른 SIM). 한도는 그 등록과 같다(설계 v1 7.1절 NOMINAL). 이 문서는 세계와 재는 방법만 G-SIM에 맞게 적는다.
- 이 문서는 `row_follow`를 스택에서 폐루프로 돌리기 전에 썼다. 이 커밋까지 스택에서 한 것: 이미지 빌드와 이미지 안 시험, 스택을 올려 그래프와 참값 자세만 본 것, 정지 상태에서 자세 되돌리기(`set_pose`)를 확인한 것. `row_follow`로 차가 움직인 실행은 0회다. ST-05의 대본 run(직진 유지 8 m, `S2_NODE_EXEC_KO.md` 7.5절)은 다른 제어기다.
- 모든 수치는 자리값이다. 결과는 **자리값 기반 SIM 결과**이고 실차 성능이 아니다.

## 2. 실행 (4회)

| 이름 | 출발 | 기대 |
|---|---|---|
| `nominal_1`, `nominal_2`, `nominal_3` | 스택을 새로 올린 뒤의 출발점 그대로(자세를 옮기지 않는다). run마다 스택을 새로 올린다 | 열 끝 정지 |
| `lateral_p040` | 스택을 새로 올린 뒤, 정지 상태에서 Gazebo `set_pose`로 출발점의 왼쪽 +0.40 m에 놓고(높이 +0.05 m에서 내려앉음) 멈춘 것을 확인한 다음 출발 | 열 끝 정지 |

- 등록 전 확인 실행(`smoke_w1`, 이미지 wf4c, 제어기를 돌리지 않음)에서 본 것: 그래프 A13(G) 통과, 스택 시작 35 s 뒤 참값 자세 x −3.62 m·y 0.00 m·속도 0, `set_pose`로 +0.40 m 옆에 놓으면 y +0.40 m가 되고 출발점으로 되돌리면 y 0.00 m가 된다. 놓은 직후 1~5 s에 차는 0.01~0.02 m/s로 뒤로 밀리고 있었다. 이 성질은 '끝에 정지'(0.02 m/s 이하) 기준에 닿을 수 있다. 기준은 빠른 SIM 등록 그대로 둔다.
- seed는 하나다(세계 seed 7, 스택 seed 0). run 사이의 차이는 실시간으로 도는 스택의 시간 흔들림과 센서 잡음이다.
- 출발 방향 어긋남, 조향 영점, 쏠림, LiDAR 끊김, 장애물 조건은 이 등록에 없다(빠른 SIM 등록이 봤다).

## 3. 재는 값

참값은 평가 쪽(검사 컨테이너)만 쓴다. 실행기 컨테이너는 runtime 볼륨과 참값 토픽을 보지 않는다(A13 R6).

- 참값 자세: `/ground_truth/odom`(모델 원점 `base_footprint` = 차체 footprint 중심). 참 속도: 그 메시지의 전진 속도.
- 통로 중심선: 장면 폴더의 생성기 메타데이터(`world_metadata.json`의 `trees`)에서, 출발 통로 양쪽 두 나무 열의 줄기 위치에 각각 최소제곱 직선을 맞추고 두 직선의 평균을 중심선으로 한다. 열 축은 그 방향이다. 출발점처럼 첫 나무보다 앞에서는 그 직선의 연장선을 쓴다.
- 횡오차: 차체 중심에서 중심선까지의 부호 있는 거리(왼쪽 +). 방향 오차: 차 방향각 − 열 축 방향.
- 주행 구간: MCU 구동 출력 duty(참값 `/sim/truth/steering`의 `drive_duty_*`, `drive_en`)가 처음 0보다 큰 때부터 마지막으로 0보다 큰 때까지.
- 열 끝 s_E: 그 두 열의 줄기 가운데 열 축 방향 좌표가 가장 큰 값(마지막 줄기 선). 열 끝 정지 위치 e = 정지 때 앞범퍼의 열 축 좌표 − s_E. 앞범퍼 = 중심 + 0.61 m·cos(방향 오차).
- 최소 여유: 차체 사각형(1.22 × 0.70 m)에서 그 두 열의 줄기 표면(생성기의 줄기 반지름)과 콘크리트 기둥(10 cm 각을 외접원 반지름 0.0707 m로 본다)까지 거리의 최솟값(run 기록 전 구간). 통로의 낮은 바위는 지형 요철이라 판정하지 않고 개수만 적는다.
- 일시정지: 구동이 시작된 뒤 실행기 틱 기록의 PAUSED 전이와 그 이유.
- 종결 뒤 조향: 실행기 `run_end` 사건의 시각(SIM 시각으로 옮긴 값)부터 3 s 동안 MCU가 받은 `C` 줄의 조향 목표(S)가 그 시각 직전 마지막 `C` 줄의 S와 같아야 한다(줄이 없으면 통과). 3 s가 기록에 다 있어야 한다. A22 규칙을 스택의 기록으로 옮긴 것이다.
- `lateral_p040`은 횡 RMSE·p95와 방향 RMSE를 주행 6.0 m 뒤부터 잰다(빠른 SIM 등록과 같다). 최댓값 한도는 처음부터 잰다.
- 판정하지 않고 적는 값: 실행기 ACTIVE 틱 가운데 통로가 유효한 틱의 비율과 무효 이유, 일시정지·hold와 이유, 주행 거리와 시간, 속도 평균, 빠뜨린 틱과 버린 스캔, 루프 시간, 종결 이유.

## 5. 유효성 (호스트 멈춤)

실차 시계 모드의 A10 규칙(`SIM_ACCEPTANCE_KO.md` 개정 10)을 그대로 쓴다. run 하나가 아래 가운데 하나에 걸리면 무효다.

- run 동안의 `/clock` RTF가 0.9 미만
- run 동안 에뮬레이터가 본 `/clock` 벽시계 틈이 100 ms를 넘은 것이 1번 이상
- SIM 멈춤 때문에 생긴 호스트 래치(`steering_status_stale` 등)

무효 run은 값을 그대로 적되 판정하지 않고, 같은 자리에서 다시 돈다. 한 자리에 다시 도는 것은 2번까지다. 그래도 무효면 그 자리는 '무효(호스트 멈춤)'로 적고 전체 판정은 '미완'이다. 스택을 올리기 전 호스트 부하 확인(`STACK_OPERATIONS_KO.md` 2절)도 기록한다.

## 6. 규칙

1. 결과를 본 뒤에는 기준·실행·재는 방법을 바꾸지 않는다. 바꿔야 하면 다시 돌리기 전에 7절에 수정 사항을 이유와 함께 먼저 적고 커밋한다.
2. 기준을 못 넘으면 그대로 적고 원인을 찾는다. 제어기·추정기의 설정을 바꾸거나 제어기 오류를 고쳐 다시 돌릴 수 있다. 그때마다 결과 문서의 반복 기록에 무엇이 실패했고 무엇을 왜 바꿨는지 남긴다. 반복은 3번까지다. 3번 뒤에도 실패면 멈추고 그 상태를 적는다.
3. 앞 반복의 실패를 지우지 않는다.

## 7. 수정 사항

### 수정 1 (2026-11-12, 반복 1의 `nominal_2` 판정을 본 뒤, 다시 판정하기 전에 적음)

- 무엇: 평가 코드가 실행기 틱 기록을 모으는 구현을 고친다. 기준, 실행 목록, 3절의 정의는 그대로다.
- 왜: `nominal_2`가 '주행 시작 뒤 일시정지 0회' 한 항목만 실패로 나왔다(이유 `await_hold`). 기록을 보니 검사가 읽은 틱 4072개 가운데 앞의 2096개는 바로 앞 세션(`nominal_1`)의 실행기 기록이었다. control 볼륨이 세션 사이에 남고, 검사가 '수정 시각이 시작 120 s 전 이후인 기록 파일'을 모두 읽으며, 두 세션의 run 번호가 같아서(2) 섞였다. 두 기록 사이에는 117.7 s의 틈이 있다. 섞인 목록에서는 이 run이 누름을 기다리던 첫 틱(`PAUSED/await_hold`)이 앞 run의 ACTIVE 틱 뒤에 오므로 '주행 시작 뒤 일시정지'로 세어졌다. 실행기 자신의 `run_end` 사건은 `pauses: 0`이고, 검사가 0.2 s마다 본 상태에도 PAUSED가 없다.
- 영향받는 값: 실행기 틱에서 나오는 것(주행 시작 뒤 일시정지, 통로 유효 틱 비율과 이유, 루프 시간, 제어기 사유 수). 참값에서 재는 값(횡·방향·속도·e·여유·정지)과 종결 뒤 조향 규칙은 영향이 없다. `nominal_1`은 앞 세션에 run이 없어 섞이지 않았다(틱 1986개, 틈 없음).
- 고친 것: (1) 검사가 이 run의 `start` 사건 뒤 기록만 쓴다(`exec_checks._run_records`). (2) 틱 목록에서 시각 틈이 20 s를 넘으면 마지막 틈 뒤만 쓴다(`gsim_follow.own_ticks`). (3) 이미 기록한 run은 그 기록 파일(`GSIM_FOLLOW_TRACE.json`의 틱)에서 다시 판정한다(`python -B -m steering.gsim_follow <run 폴더>` → `GSIM_FOLLOW_REJUDGED.json`). 원래 출력(`GSIM_FOLLOW_RUN.json`)은 그대로 두고 결과 문서에 두 판정을 다 적는다.
- 이미지 `wf4c`의 검사 코드에는 이 결함이 있다. 스택이 돌리는 프로세스(실행기, 제어기)는 같다. 이 수정 뒤의 세션은 고친 검사 코드를 검사 컨테이너에만 붙이거나, 기록에서 다시 판정한다.

## 8. 이 등록이 보이지 않는 것

- 실차 성능. 모든 값이 자리값이다(조향 장치 치수, 속도표, 지연, 한도, 과수원 모델).
- 다른 seed의 과수원, 10/10 통로(W2), 굽은 열, 열 끝 너머의 벽, 사람·장애물.
- 출발 방향 어긋남, 조향 영점, 쏠림, LiDAR·IMU 끊김, 조작 신호 끊김, MCU·브리지 고장(빠른 SIM 등록과 A17·A19가 따로 본다).
- SIM 시계 모드. 한 번 눌러 시작(설계 v2 R32)은 아직 없다. 누름 박동은 검사가 보낸다.

## 9. 실행

스택은 `tools/steer_sim/stack.py`로 올린다(프로젝트 `ubts-steer-<작업>`, `UBTS_STEER_SCENE=w1_force`, `UBTS_STEER_CLOCK=wall`, `UBTS_STEER_IMAGE=ubts-steer-sim:wf4c`, 서비스 sim steer recorder executor, 프로필 executor). run 하나:

```
python -I tools/steer_sim/stack.py run --project ubts-steer-<작업> -- \
    python3 -B -m steering.exec_checks follow --run nominal_1 --out /runs/nominal_1
```

`/runs/<이름>/`에 `GSIM_FOLLOW_RUN.json`(잰 값, 기준별 판정, 유효성)과 `GSIM_FOLLOW_TRACE.json`(참값 경로, 실행기 틱, 장면 기하)이 생긴다. 결과와 그림은 `STEER_FOLLOW_GSIM_RESULT_KO.md`에 적는다.
