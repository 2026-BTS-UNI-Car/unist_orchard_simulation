row_executor 운용·프로토콜 노트 (2026-10-22, 주말 현장 MVP-0/MVP-1용)
=====================================================================
[조향 브랜치 사본 2026-11-09] 단일열 작업 546fa8c에서 가져온 문서다. 회전(turn_*, TURN_ASSIST.txt)·재생(replay_*, row_shadow_replay.py)·convert_1003.py·row_gate_report.py는 가져오지 않았다. 바꾼 것: docs/steering/EXECUTOR_IMPORT_KO.md.
범위: tools/row_executor/{config.py, guard.py, core.py, bridge_client.py} + vendor/ + tests/.
이 패키지는 스스로 모터 명령을 보내지 않는다. Runner는 Decision만 돌려주고, BridgeClient를 쓸지는 호출자
(executor_main, 아직 미작성)가 정한다. 기본값 motor_output_enabled=false(SHADOW). ROS import 없음.
Jetson 설치·실차 시험은 하지 않았다. 아래 "확인"은 단위·프로토콜 시험(4절) 범위다.

1. 파일
-------
  config.py      ExecutorConfig(frozen), strict JSON(load_config/loads/dumps), validate(), feasibility()
  guard.py       OutputGuard(마지막 출력 검사), Backstop(L-2 m 거리, 1.15(L-2)/v 시간)
  core.py        load_vendor(sha256 검증 후 import), ScanAdapter, ImuYawRate, Runner, Decision
  bridge_client.py  BridgeClient(UnixSocketTransport), arm_precheck, recovery_hint, RECOVERY_PROCEDURE
  vendor/        SIM estimator.py / controllers.py / scan_corridor.py (+원래 __init__.py) 바이트 그대로.
                 출처 2026-10-19 cross-alley SIM 브랜치 커밋 1eb9c07261120b0242edf495e88f3e680bbe40a4,
                 vendor/SOURCE_MANIFEST.json에 sha256·bytes·git blob. load_vendor()가 매번 다시 해시를 계산하고
                 다르면 import를 거부한다(VendorError). 수정 금지: 바꿀 일이 있으면 새로 vendoring하고 manifest를 갱신.
  config.field_shadow.example.json  현장 기본 SHADOW 설정(= ExecutorConfig() 기본값).

2. ESP 브리지 프로토콜 규칙 (DASH = 대시보드 폴더, 읽기 전용 참조: sim_paths 'dashboard_dir')
-----------------------------------------------------------------------------------
  - 소켓 /run/ubts-rover/control.sock, JSON 한 줄. 연결 하나에 요청 하나다(Handler.handle가 한 줄만 읽고 닫음).
    UnixSocketTransport는 요청마다 새로 연결한다. 시험에서 연결 수 = 요청 수 = 서버 accept 수를 확인했다.
  - drive는 0/0을 포함해 항상 deadman:true. deadman이 없으면 invalid_drive → hard stop + lease 삭제
    (rover_control_core.py dispatch). 운용자의 hold-to-run은 실행기 쪽 신호이고 브리지 deadman 필드와 무관하다.
    hold를 놓으면 실행기는 drive(0,0, deadman:true)를 계속 보낸다 → lease 유지(moving=False라 0.75 s 입력 만료 없음,
    owner TTL 30 s는 drive마다 갱신, ticket 1.5 s는 drive마다 새로 발급).
  - 0이 아닌 drive는 0.75 s 안에 갱신해야 한다. 아니면 브리지가 input_expired로 정지하고 lease를 지운다.
    실행기는 10 Hz(send_hz) 전송 + 0으로 바뀌는 순간 즉시 전송(executor_main 몫).
  - stop은 lease 없이 누구나 보낼 수 있다(대시보드·관찰자 폰 STOP). 응답 "stop_requested"는 출력 0 확인이 아니다.
    출력은 status()['outputs']로 확인한다. STOP 직후 20 ms 안에 들어온 요청은 stop_barrier로 거부된다.
  - BridgeClient 상태: DISARMED → arm() → ARMED → stop() → DISARMED. 어떤 오류든 LATCHED
    (전송 오류·시간 초과·형식 오류·ok:false 전부: control_not_owned, stale_input_rearm_required, invalid_sequence,
    request_expired, control_busy_stopped, stop_barrier, status ok:false 등). LATCHED 진입 때 lease를 갖고 있었으면
    best-effort op stop을 보낸다. lease가 없을 때(arm 거부 등)는 다른 소유자를 멈추지 않도록 stop을 보내지 않는다.
    (1일차 검토 S7) drive가 control_not_owned 또는 stop_barrier로 거부되면(LEASE_GONE_ERRORS: 다른 클라이언트의 STOP·
    입력 만료로 우리 lease가 이미 없다) stop을 보내지 않는다. 그 사이 사람이 대시보드에서 Arm한 새 lease를 지우지 않기
    위해서다(counts.latch_stop_skipped). lease가 남아 있을 수 있는 오류(전송 오류·시간 초과·request_expired·
    control_busy_stopped·stale_input_rearm_required·invalid_sequence 등)는 그대로 stop을 보낸다.
  - 자동 재arm 없음: LATCHED에서는 drive()가 아무것도 보내지 않고, arm()은 acknowledge_latch()(운용자의 명시적 동작)
    전까지 거부한다. 정상 종료 stop 뒤에도 arm은 운용자의 Start가 있을 때만 부른다.
  - arm 전 점검(arm_precheck): status ok, connected, firmware UBTS_WHEEL_PWM_V2, last_error 없음, state disarmed·
    armed false(다른 클라이언트가 잡고 있으면 control_in_use와 같은 상황), moving false, snapshot 나이 ≤ 2 s.
    점검 통과 후 arm 사이에 대시보드가 먼저 arm하면 arm_refused:control_in_use로 LATCHED(stop 안 보냄).
  - 정상 종료 순서(executor_main 몫): drive(0,0) 계속 → 추정기 still 또는 terminal_stop_wait_s(1.5 s) → stop(lease 해제)
    → 이후 사람이 대시보드에서 수동 조종 가능. 운용자 STOP 버튼은 stop(latch=True).

3. Runner 규칙 (core.py docstring이 원문)
---------------------------------------
  - Start(row_len_m 필수) → 새 추정기, Backstop 무장, PAUSED('await_hold').
  - PAUSED → ACTIVE: 새 hold 누름(상승 에지)이 있고, 그 순간 LiDAR·IMU가 fresh_recover_s(1 s) 이상 연속 신선할 때만.
    Start 전부터 누르고 있던 것은 누름으로 치지 않는다. 신선도 1 s 전 누름은 무시('press_ignored_inputs_not_fresh')되고
    놓았다가 다시 눌러야 한다. 재개마다 RowController를 새로 만든다(일시정지가 drive_no_response로 읽히지 않게).
  - ACTIVE → PAUSED(0/0): hold 해제, 입력 stale(LiDAR > 0.45 s, IMU > 0.4 s; C1 gate P2), 루프 정지(tick 간격 > 0.35 s, stall_guard),
    외부 pause(감시 스레드), 통로 상실(아래). 단, 제어기가 종결 정지를 이미 정한 뒤(STOP_REQUESTED, pending 'hold'/'front',
    'wait_corridor' 외 모든 pending)라면 일시정지 대신 그 종결 이유로 ENDED가 된다(1일차 S1/F1; end_note
    'terminal_stop_pending_at_<why>'). 백스톱 등 다른 종결이 먼저 오면 end_note 'controller_pending:<사유>'.
  - 통로 상실(1일차 S2/F7): 제어기가 통로 상실 정지(STOP_REQUESTED, pending 'wait_corridor')를 시작하거나 'start'가 아닌
    REACQUIRE에 들어가면 PAUSED('corridor_lost' / 'reacquire_needs_press'), 제어기는 버린다. 재개 = 신선한 입력 + 추정기 정지
    (still ≥ still_confirm_s 0.4 s) 뒤의 새 누름(그 전 누름은 'press_ignored_not_standstill'). 센 거리 5 m 안 4번째 상실은
    종결 'corridor_lost_repeat_limit'.
  - stale 단일 규칙: stale → 0/0, PAUSED. 데이터가 돌아와도, 계속 누르고 있어도 다시 출발하지 않는다. 신선 1 s 뒤
    "새 누름"만 재개한다. 한 run에 stale이 max_stale_events(3)를 넘으면 종결 'stale_repeat_limit'.
    vendored 제어기 자체의 자동 복구(1 s 신선 + 정지 → REACQUIRE)는 쓰이지 않는다(stale 입력으로 step하지 않고,
    그래도 recoverable HOLD가 오면 같은 규칙으로 처리).
  - 종결(ENDED, 재시작은 새 Start만): 제어기의 모든 종결 HOLD(row_end_candidate, front_blocked, side_blocked,
    corridor_not_acquired, drive_no_response, ...; 모르는 이유도 종결), 종결 정지 중의 일시정지(위),
    corridor_lost_repeat_limit, drive_no_response_repeat(2일차 N9: run 전체에서 출력 중 무움직임 누적 > 6 s, 움직임이 보이면 0),
    guard_violation:*, row_distance_backstop, row_time_backstop, backstop_odometry_invalid, stale_repeat_limit,
    stall_guard_repeat_limit(4번째), clock_regression, end_run(운용자).
  - MVP-1 정지 = min(row_end_candidate, 주행거리 ≥ L-2 m, 이동 시간 ≥ 1.15·(L-2)/v_measured).
    이동 시간은 마지막 명령이 0이 아니거나 추정기가 정지를 보고하지 않는 동안만 센다(정지해 기다리는 시간은 안 셈).
    주행거리는 추정기가 움직임을 보고하는 tick의 증가분만 센다(1일차 F4; 정지 중 정합 지터는 still_excluded_m). 차는 L−2에
    정지 거리를 더한 곳(0.45 m/s면 약 L−1.7 m)에 선다(backstop.expected_rest_m).
    v_measured가 없으면(SHADOW) 시간 백스톱은 꺼진다. 마지막 2 m와 headland 회전은 사람이 한다.
  - drive_no_response: 첫 전진 명령 후 약 3 s(MCU ramp 1 s + grace 1 s + 무반응 1 s, scan 하나 더)에 0 출력,
    정지 확인 후 약 +0.7 s에 종결. 바퀴를 띄운 벤치에서는 이것이 정상이다(시험: FOLLOW 후 3.0–3.3 s).
  - 제어기 시계: vendored RowController는 since=0.0으로 시작한다(SIM은 t=0에서 시작). 단조 시계(부팅 후 수천 s)
    그대로 step하면 REACQUIRE 6 s 시간 초과가 즉시 나서 모든 run이 corridor_not_acquired로 끝난다(이번에 발견).
    Runner는 제어기를 "재개 시각 = 0"인 상대 시계로 step한다. snapshot에는 나이·기간만 있어 다른 영향은 없다.
  - side 규칙(continuous_side): 새 제어기는 side_blocked를 서로 다른 scan 2개로 확인한다. 재개 직후 차체 옆
    hard margin 안에 이미 물체가 있으면 FOLLOW 출력(예: 55/55)이 약 0.1 s 나간 뒤 정지한다(MCU ramp로 실제 duty는
    약 10 %p). 차체 자기반사가 마스크되지 않으면 출발 직후 side_blocked 종결이 난다(시험으로 확인, body_mask로 해소).

4. 파라미터 실현 가능성 (config.validate / feasibility)
------------------------------------------------------
  - 허용 모드: continuous, continuous_side만(전진 전용, pivot·REDUCE 없음). 제어기 override는 허용 목록만
    (pivot·turn·fallback·tick·side bias 불가).
  - 안쪽 바퀴: base - max_diff ≥ breakaway + inner_margin, reduce - max_diff ≥ breakaway + inner_margin.
    breakaway(C2)가 있으면 항상 검사(위반은 설정 오류). inner_margin(기본 10)은 SHADOW에서 조정 가능(MOTOR는 ≥ 10, 2일차 N1).
    rolling_breakaway_duty_pct(C3b)도 쟀으면(1일차 F2): 주행 중 base/reduce − max_diff ≥ rolling + margin, 정지 출발 시
    base/reduce ≥ breakaway + margin. Runner는 추정기가 지속 움직임을 보기 전(still 아님, 정합 유효, 0.10 m/s 이상; 0.05 미만이면
    해제)에는 차등을 평균 유지한 채 줄여 안쪽 바퀴를 breakaway + margin 이상으로 두고, Guard는 그때 static, 움직인 뒤에는 rolling
    기준으로 검사한다.
    예: base 55 / diff 20 / B_fwd 44 → 안쪽 35 < 54로 거부(FEASIBILITY_CRITIQUE H1). reduce 기본값 = base.
  - OutputGuard 실행 중 검사: 정수, 음수 금지(후진·pivot), duty ≤ duty_cap, |L-R| ≤ diff_cap,
    주행 중 min(L,R) ≥ breakaway + margin(inner_rule_enabled). 위반 → 0/0 + 종결 guard_violation:<이유>.
    duty_cap ≥ base + diff, diff_cap ≥ 2·diff가 아니면 설정 오류(정상 출력이 가드에 걸리는 설정 금지).
  - motor_output_enabled=true에는 측정값이 모두 필요: breakaway_duty_pct(C2), v_measured_m_s(C3, ≤ max_speed_m_s 0.5),
    measured_yaw_at_max_diff_deg_s(C5, ≥ 2 °/s, max_yaw_rate ≤ 0.6×측정값), measured_stop_distance_m(C7, 2일차 N8: 정지 모델이
    v_measured에서 측정 이상이고 모델 + front_margin ≥ 측정 + 0.35), inner_rule_enabled=true.
    SHADOW에서는 모르는 값이 있어도 되며 status 'unknown'으로 보고한다.
  - MOTOR(열 추종·보정)에서는 안전 관련 값을 평가된 기본값보다 느슨하게 못 한다(1일차 S6 + 2일차 N1; config.py 문서열과
    2일차 블록 DAY2_MOTOR_LIMITS / DAY2_CONTROLLER_LIMITS가 원문). 보정 설정은 base ≤ 60, duty_cap ≤ 75, max_speed ≤ 0.5(N2).
  - 현장 설정 onsite_update(2일차 R2): diff를 낮추면 measured_yaw_at_max_diff_deg_s를 × 새 diff / 파일 diff로 줄이고
    max_yaw_rate_deg_s를 0.6 × 그 값(0.1 단위 내림, 파일 값 이하)으로 낮춘 뒤 다시 검사한다. 권한 < 2 °/s면 거부.
  - 이 검사는 설정 파일 단계다. 실행기 CLI 플래그(--motor-output)·화면 Arm은 executor_main에서 따로 요구해야 한다.

5. bench 패턴 (바퀴 띄움 V7 전용)
--------------------------------
  - profile 'field'에서는 bench_pattern·bench_ack가 있으면 설정 오류. load_config(path, expected_profile='field')는
    profile이 다른 파일을 거부한다. Runner.start_bench는 profile 'bench'에서만 동작.
  - profile 'bench'는 bench_ack == 'WHEELS_OFF_GROUND' 필요. 각 단계 ≤ 10 s, 합 ≤ 60 s, 단계 ≤ 32개, 전진만,
    가드 규칙 동일. 실행 중에도 hold·stale 규칙·OutputGuard를 그대로 거친다(일시정지 후 이어서, 끝나면 종결).

6. ESP 브리지 FAULT / EspMotor.error 복구 절차 (bridge_client.RECOVERY_PROCEDURE와 같은 내용)
-----------------------------------------------------------------------------------------
  원인 두 가지는 브리지 프로세스 안에서 풀리지 않는다:
   (a) MCU watchdog → EspMotor.error='mcu_watchdog_rearm_required'(지우는 코드 없음) → connected=false, arm 거부
       (verified_esp_v2_required). 시험: device_unavailable로 lease 삭제, 실행기 LATCHED, 재arm 점검 실패 확인.
   (b) WheelController의 RuntimeError(예: 'PC heartbeat expired; wheels disabled')가 Bridge.step의
       except (ControlError, ValueError)를 빠져나감 → main 루프가 영구 'fault' 상태, 이후 요청은 0.4 s 뒤
       control_busy_stopped. 시험: main 루프를 그대로 따라 한 루프로 확인(main 소스 조각 일치도 검사).
  절차:
   1. 차량을 안전하게: 물리 E-stop 누름 또는 바퀴 띄움. 브리지 재시작 때 ESP 리셋 출력 튐 가능(미검증).
   2. 실제 컨테이너 이름·상태 확인: docker ps -a --filter name=esp-rover-bridge --format '{{.Names}} {{.Status}}'
      (compose의 container_name은 unist-orachard-ros2-esp-rover-bridge; 설치된 이름을 그대로 쓴다),
      runtime/rover_bridge_status.json
   3. docker restart <2의 이름>  (그 컨테이너만)
      docker compose up/down/restart는 절대 쓰지 않는다(compose가 옛 대시보드 이미지로 되돌림, 작업 루트 지침 문서 10/13 표).
   4. status가 connected=true, firmware=UBTS_WHEEL_PWM_V2, state=disarmed, last_error=null인지 확인.
   5. 실행기 화면에서 latch 확인(acknowledge) 후 Start(자동 재개 없음).
   USB를 다시 꽂아 장치가 다시 잡혀 restart로 열리지 않으면 compose로 재생성하지 말고 중단·보고한다(장치 매핑은
   컨테이너 생성 시점 고정).

7. 시험 (2026-10-22 실행 결과)
-----------------------------

             python3 -B -m unittest discover -s tools/row_executor/tests -p "test_run_script.py"
