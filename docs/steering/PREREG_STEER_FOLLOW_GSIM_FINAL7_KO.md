### 0.1 B 실패 원인 (6단계 B run 1)

기록: 6단계 기록 폴더의 B 세션과 그 스택 볼륨의 브리지 사건 기록·에뮬레이터 기록(읽기 전용으로 복사, 7단계 기록 폴더 `b_analysis/`).

- lease TTL 만료가 아니다. 브리지가 **상태 줄 틈 래치** `steering_status_stale`을 걸고(SIM 185.150 s) 제어를 멈추며 lease 를 거뒀고,
  다음 drive 가 `control_not_owned`로 거절됐다(SIM 185.217 s). 실행기는 이를 `steering_feedback_stale`로 끝냈다(안전하게 섬).
- 브리지 기준은 `host_faults.status_gap_ms` 150 ms, MCU 상태 줄 20 Hz. 브리지는 `--clock sim`이라 틈을 **자기 /clock 구독의 SIM 시간**
  으로 잰다.
- 에뮬레이터(모의 MCU)는 SIM 시간으로 50 ms 마다 빠짐없이 상태 줄을 냈다. 그러나 SIM 184.8947 -> 184.9447 s 한 걸음에 벽시계 0.340 s 가
  걸렸다(앞뒤 걸음 0.03~0.10 s). 그동안 같은 컨테이너의 브리지는 쌓인 /clock 을 받아 SIM 시간을 92 ms(벽) 동안 192 ms 나아갔다. 두
  프로세스의 단조·벽시계 차이로 맞추면, 에뮬레이터가 SIM 184.9447 줄을 냈을 때 브리지의 SIM 시간은 약 185.0, 184.9947 줄 때는 약
  185.125 였다. 모의 MCU 의 SIM 시간이 브리지의 SIM 시간보다 0.1~0.25 s 뒤처져, 브리지는 기준대로 래치했다.
- 갈래: 시계 영역 불일치가 아니라(둘 다 SIM 시계), **각 프로세스가 /clock 을 따로 받아 한 프로세스만 멈추면 두 SIM 시계가 갈라지는**
  SIM 의 성질이다. 실차의 MCU 는 따로 돌아 이런 갈라짐이 없다. 래치·브리지·에뮬레이터 코드의 결함은 찾지 못했다. 그때 E 등급 5 s
  평균 79.7 %(포화), P 등급 25.9 %, 전체 최대 58.8 %.
- 고침(한도는 그대로): 에뮬레이터·브리지·센서 계약 프로세스의 CPU 를 줄여 덜 멈추게 한다(0.2). 모의 MCU 를 Gazebo 와 같은 걸음으로
  묶는 것(Gazebo 가 에뮬레이터를 기다림)은 큰 재설계라 하지 않는다(결과 문서에 제안으로 적는다).

### 0.2 스택 CPU 줄이기 (wf10, 정하는 것은 그대로)

- 브리지 래퍼(`dashboard/scripts/steer_rover_bridge.py`, SIM 시계 모드만): 2 ms 폴링 대신 ROS 대기에서 잠들고, /clock 표본이나 제어
  요청(요청을 넣을 때마다 깨우는 guard condition)이 오면 깬다(최대 50 ms). STOP 이 아직 걸려 있으면 전처럼 2 ms 폴링. 격자 걸음은 SIM
  시간과 걸린 STOP 에만 달려 있어 결정은 같다. SIM 시계 모드의 브리지 노드, 에뮬레이터 노드, 센서 계약 노드는 파라미터 서비스·타입
  설명 서비스·/rosout 이 없다(구독·QoS·콜백·발행 그대로). 실차의 벽시계 모드는 바뀌지 않는다.
- 자율주행에 쓰는 센서(LiDAR, IMU, 조향 에뮬레이터)의 충실도·주기·지연 모델, 카메라 해상도·fps, 안전 한도(조향 상태 틈 150 ms, 실행기
  조향 상태 0.3 s, MCU 명령 TTL, 신선도·blind 상한, 속도 조절기 최저 속도, 운영자 기한 1.0 s)는 하나도 바꾸지 않는다.
- 개발 확인(판정 아님, 7단계 기록 폴더, wf9 위에 세 파일을 붙인 측정 스택 + 열 추종 1 run 씩, 컨테이너별 /proc CPU): VM 안 CPU 시간은
  vCPU 가 Windows 의 E 코어에 놓이면 커져서(쉬는 스택 전체가 같은 판에서 186.8 % 와 273.5 %, 그때 E 등급 26.4 % 와 46.7 %), 바뀌지 않은
  프로세스 합에 대한 몫으로 비교했다. 브리지 래퍼: 쉼 0.256 -> 0.144, run 중 0.247 -> 0.167(약 33~44 % 줄음; 루프 걸음당 폴링 6.6 ->
  2.5). 에뮬레이터·센서 계약: 가를 만큼 줄지 않음. run 중 바뀌지 않은 몫이 비슷한 두 세션의 스택 합 275.2 % -> 253.6 %(한 코어 =
  100 %). 열 추종 1 run 은 base 통과, 첫 개발판은 내가 같은 컨테이너에 프로파일러를 붙인 동안 실행기 루프가 0.4 s 멈춰 `stall_guard`
  (내 측정이 끼어든 것이라 판정에 쓰지 않음), 다음 판(커밋 `f235395`과 같은 파일)은 통과.
- 출력 같음 회귀(잠금 아래, base `51efae3` 대 head `835bd82`, 2026-11-14 04:55~05:04 KST): 차동 기준 에피소드 9 중 8 같음(트리 경로
  칸만 다름), 빠른 SIM `steer_follow_v1` 15 회 직렬 로그·trace 15/15 같음(둘 다 15/15 기대대로), 실행기 기록은 시간 칸(`loop_ms`, `ph`,
  `ms`, `proc_ms`, `wall`, `ww`, `wm`)과 트리 이름을 빼면 15/15 같음, T1 안전 대본 71 개 직렬·trace 71/71 같음(둘 다 71/71 통과, 끝
  이유 바뀜 0). 이 회귀는 바뀐 세 파일의 경로(Gazebo 스택의 브리지 래퍼 SIM 시계 루프, 에뮬레이터·센서 계약의 ROS 노드)를 지나지

## 1. 공통

6단계 등록 1절 그대로(SIM 시계, 세션마다 새 스택, healthy 뒤 120 s, 판정 단계 5 s 창 RTF 0.5 미만은 호스트 고장으로 다시, 부하 확인
기록, 사용자 스택은 내리고 무거운 잠금, Windows 프로세스별 표본기, A·B 측정 스택 포트 18091). 이미지는 `ubts-steer-sim:wf10`(이 등록을
넣은 커밋의 깨끗한 작업 트리에서 등록 run 전에 빌드, 매니페스트 = 커밋 blob, compose 기본 태그). 바꾸거나 더하는 것:

- **(가) 호스트 조용함 사전 확인**: 판정하는 run 바로 전에 표본기의 마지막 **30 s** 에서 Windows 전체 CPU 평균 **45 % 미만**(6단계
  그대로) **그리고** 효율 등급 0(E 코어) 평균 **50 % 미만**. 5 s 마다 보고 최대 900 s 기다린다. 기다린 시간과 두 평균을 적는다. 900 s
  가 지나도 아니면 그대로 시작하고 그렇다고 적는다.
  - 까닭: 6단계 등록의 사전 확인 30 s E 평균은 통과·실패 run 모두 28.7~44.9 % 였다. 50 % 는 그 위에 여유를 두고, E 포화(약 80 %) 구간과
    떨어져 있다.
- **(나) 호스트 고장 규칙**: 실패한 run(A, F)이나 실패한 세션(B)은, 그 **실패 사건 전 5 s** 표본에 (6단계) 전체 CPU **70 % 이상** 표본이나
  **1.0 s 이상** 늦은 표본이 있거나, (새로) 그 표본들의 **E 등급 평균이 75 % 이상**일 때만 호스트 고장(무효, 세지 않음)으로 적는다.
  무효인 자리는 사전 확인 뒤 **run 당 최대 두 번** 다시 돈다(A·B 새 스택, F 같은 스택에서 start·reset 한 번 더). 시도는 무효든 아니든
  모두 적고 지우지 않는다. 세 번 다 무효인 자리는 **판정 못 함**으로 적는다(합격으로 세지 않는다). 호스트 고장이 아닌 실패는 실패다.
  - 까닭(6단계 등록 표본기): 실패 사건 전 5 s E 평균은 B 79.7, F 실패 79.0·79.5, F 무효 67.1 % 였다. 통과 run 의 1 s 표본 546 개 중 5 s
    E 평균이 75 % 이상인 것은 58 개(10.6 %, 70 % 이상은 16.1 %)였다: 통과 run 도 E 포화 구간을 지나므로, 실패가 우연히 포화 구간에 걸릴
    확률이 약 11 % 있다. 이 규칙은 포화가 실패의 원인임을 증명하지 않는다(결과 문서에 그대로 적는다).
- **(다) B 의 실패 사건 시각**: 실행기 기록의 **실제 멈춘 시각** = go 뒤 처음으로 상태가 ACTIVE 가 아니면서 그 이유가 대본이 일으킨 것
  (`operator_stop`, `operator_link_lost`, 화면 STOP 의 한 틱 `hold_released`)이 아닌 틱의 벽시계(세션 시계 차이로 Windows 시각으로
  바꾼다). 그런 틱이 없으면(화면만의 실패) 6단계처럼 처음 실패한 등록 항목 검사의 벽시계.
- run 마다 적는 것: 6단계 것 + run 동안의 E·P 등급 평균.
