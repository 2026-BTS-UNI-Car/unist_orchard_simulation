# Gazebo 관절 직접 조종 시연 (P5 이른 시연)

- 작성: 2026-11-09. 설계 8.3 P5 "이른 시연" 기록이다.
- 코드: `sim/ubts/steering/gz_direct_drive.py`. 모델 고침은 `gz_model.py`, `gz_assemble.py`, 실시간 보조는 `gz_probe.py`(모델 쪽 기록은 `GZ_MODEL_KO.md`).
- 이름: **관절 직접 조종 시연**(joint direct-drive demo). V3 규약, 에뮬레이터, 브리지, 안전 사슬이 없다. 평가에 쓰지 않는다. 로그 줄, 그림 위 글자, 그래프 제목, 캡션에 모두 이 이름을 적는다.
- V3 규약, ESP 에뮬레이터, 브리지 래퍼, 안전 사슬이 있는 헤드리스 스택은 P6a다(`P6A_HEADLESS_KO.md`). 이 시연과 섞지 않는다.
- 2026-11-09 리뷰 고침(fix_wf2b): 차 전체 질량을 프로필 30 kg에 맞춘 모델(`GZ_MODEL_KO.md` 1·11절)로 그림·영상을 다시 만들었다(5.1절). `run.json`·`circles.json`에 출처(`provenance`: 커밋, 돈 파일 SHA 묶음, 월드 SDF SHA, 구동기 빌드)와 네이티브 구동기의 빌드 기록을 남긴다(리뷰 F2).
- 모든 값은 자리값 프로필(`front_steer_v0_placeholder`)에서 온다. 3단계 그림·영상(10절)은 프로필 v0.1(`front_steer_v0_1_placeholder`)과 구 바퀴 충돌로 다시 만들었다. 결과는 "자리값 기반 SIM 결과"다. 현장 검증이 아니다.

## 1. 무엇을 하는가

- 조향: 대본(또는 키보드)이 등가 조향 목표를 준다. 공유 조향 구동기 모델(`backend_api`, test_servo 모드)이 그 목표를 따라 바퀴각을 낸다. 그 바퀴각을 Gazebo 조향 관절 목표로 보낸다. gz_probe와 같은 방식이다(물리 한 스텝마다 모델 한 스텝, 스텝 k+1 끝의 바퀴각을 스텝 k+1 목표로 보냄).
  - 구동기 모델: `--backend native`(C++ L1, 프로필 기본 수준) 또는 `--backend l0`(Python L0).
  - 시연 실행에서는 0점 오차와 가변저항 보정 잔차를 0으로 둔다(`DEMO_OVERRIDES`, 결과 표지 `overrides.label = gz_demo_zero_offset_0`). 직진 목표가 곧게 가고, 원이 R = L / tan δ와 비교되게 하려는 것이다. `--keep-zero-offset`이면 프로필 뽑기를 쓴다.
- 구동: 대본의 duty를 MCU 램프(100 %/s)로 바꿔 바퀴 속도 목표(duty × ω0)로 보낸다. 힘 모드 DC 직선(`GZ_MODEL_KO.md` 2절)이 그대로 쓰인다.
- 대본(`--script`):

| 이름 | 월드 | 내용 |
|---|---|---|
| `w0_turns` | W0 | δ +15°로 왼쪽 원호 → 12 s에 −15°로 오른쪽 원호 → 24 s에 duty 0(MCU 램프) → 조향을 유지한 채 정지. 목표 0.5 m/s의 duty |
| `w0_slalom` | W0 | ±15° 사인, 주기 8 s |
| `w0_circle` | W0 | 고정 조향 원(기본 +15°) |
| `w1_straight` | W1 | 열 사이 직진, 작은 보정 두 번(12~20 s: +5°/−5°/+5°, 26~34 s: −5°/+5°/−5°, 각 2/4/2 s, 열린 고리 시간표), duty 1.0, 44 s에 정지 |
| `circles` 명령 | W0 | 차 6대가 ±5/10/20°로 고정 조향 원(목표 0.5 m/s, 125 s). 카메라 없음 |
| `keyboard` 명령 | W0/W1 | a/d 조향 목표 ±2°, w/s duty ±0.05, 스페이스·x duty 0, c 조향 목표 0, q 끝 |

- W1 duty 1.0: 자리값 τ_stall 1.6 N·m에서는 예전 단단한 모델이 duty 0.48·0.8로 W1에서 멈췄다(6절). 고친 모델은 0.48로도 간다. 시연은 열 끝까지 가도록 1.0을 쓴다.

## 2. 시연 카메라

- 차량 모델은 바꾸지 않는다. 시연 카메라는 별도 정적 모델(`demo_cam_<시점>`)이다. 카메라 센서 하나만 있고 시각 요소, 충돌, 질량이 없다.
- fixture 실행에서는 물리 스텝마다 `set_world_pose_cmd`로 카메라 모델을 옮긴다. 차의 평면 자세(x, y, yaw, 높이)만 따른다. 정적 모델도 이렇게 옮겨진다(실측).
- 장면을 만들 때 차량 모델의 정규화 SHA-256(공백 무시)을 기록하고, 카메라를 붙인 뒤 다시 계산해 같은지 본다. `check` 명령도 다시 본다.
- 차량 자체 카메라(640×360, `/sim/camera`)는 그대로 둔다. W1 그림 일부는 그 카메라 영상이다.

| 시점 | 종류 | 설정(SIM_ASSUMED, 표시용) |
|---|---|---|
| `chase` 추격 | 따라감 | 차 기준 (−2.05, 1.0, 1.2) m에서 (0.35, 0.05, 0.2) m를 봄, 수평 시야 60° |
| `top` 위에서 | 따라감, 수직 아래 | 차 원점 위 10 m, 수평 시야 10.5°(거의 정사영). 그림 오른쪽 = 차 앞, 그림 위쪽 = 차 왼쪽. 1.75 m·55°로 처음 찍었을 때는 원근 때문에 높이 0.44 m의 차체 판이 바퀴를 모두 가렸다 |
| `front` 앞쪽 | 따라감 | 차 기준 (2.0, 1.2, 0.95) m에서 (0.25, 0, 0.18) m를 봄 |
| `overhead` 고정 머리 위 | 고정, 수직 아래 | 출발 자세 기준 (3.3, 2.5) m 위 11 m, 수평 시야 60°. 그림 오른쪽 = 출발 앞, 그림 위쪽 = 출발 왼쪽 |

- W1에서는 따라가는 카메라가 3.8 m 통로 안에 있도록 옆 거리를 줄인다(`WORLD_VIEW_OVERRIDES`): 추격 (−2.1, 0.55, 1.25) m, 앞쪽 (2.1, 0.6, 0.9) m.

- W0 시연 장면에는 1 m 바닥 격자(얇은 시각 요소, 충돌 없음, `demo_ground_grid`)를 둔다. 따라가는 카메라에서 움직임이 보이게 하는 표시다. 바닥이 한 색이라 격자가 없으면 차가 서 있는 것처럼 보였다.
- 그림 위 글자: 한글 글꼴 경로를 `UBTS_DEMO_FONT`(또는 `--font`)로 준다. 이 PC에서는 `C:/Windows/Fonts/NanumGothic.ttf`를 컨테이너에 읽기 전용으로 붙였다. 글꼴이 없으면 영어 글자로 쓴다.

## 3. 실행 방법

이미지는 P5 이미지 `ubts-steer-sim:p5`를 쓰고 작업 트리를 읽기 전용으로 붙인다(이 브랜치의 새 이미지 ID 두 개를 이미 다 썼다). 출력은 저장소 밖 폴더다.

3단계(2026-11-09, 10절)부터는 `ubts-steer-sim:wf3`의 자기 소스로 돈다. 아래 명령에서 작업 트리 마운트(`-v …:/work:ro`)와 `PYTHONPATH`, `UBTS_STEER_BUILD_DIR`를 빼고 `-w /opt/ubts/sim/ubts`를 준다(이미지 안 네이티브 빌드 `/opt/ubts/steer_native_build`를 그대로 쓴다). 컨테이너에는 `UBTS_STEER_SOURCE_COMMIT`, `UBTS_STEER_SOURCE_STATUS_SHA256`을 넘긴다(`GZ_MODEL_KO.md` 5절).

```powershell
python -I D:/Develop/UBTS/steering-sim-20261108/tools/docker_budget.py acquire --label <label> --gib 4
docker run --rm --cpus 4 --memory 4g --network none --name ubts-steer-<label> `
  -v D:/Develop/UBTS/sim-wt-steering-20261108:/work:ro -v <출력 폴더>:/runs `
  -v C:/Windows/Fonts/NanumGothic.ttf:/fonts/NanumGothic.ttf:ro `
  -e PYTHONPATH=/opt/ubts/raydeps:/work/dashboard:/work/sim/ubts -e PYTHONDONTWRITEBYTECODE=1 `
  -e UBTS_STEER_BUILD_DIR=/runs/build -e UBTS_DEMO_FONT=/fonts/NanumGothic.ttf -w /work/sim/ubts `
  --device /dev/dxg -v /usr/lib/wsl/lib:/usr/lib/wsl/lib:ro -v /usr/lib/wsl/drivers:/usr/lib/wsl/drivers:ro `
  -v /mnt/host/wslg/.X11-unix:/tmp/.X11-unix:ro -e UBTS_RENDER_ENGINE=ogre -e UBTS_HEADLESS_RENDERING=0 `
  -e LIBGL_ALWAYS_SOFTWARE=0 -e GALLIUM_DRIVER=d3d12 -e MESA_D3D12_DEFAULT_ADAPTER_NAME=Intel -e DISPLAY=:0 `
  -e EGL_PLATFORM=x11 -e LD_LIBRARY_PATH=/usr/lib/wsl/lib -e GZ_PARTITION=ubts-steer-demo `
  ubts-steer-sim:p5 bash -c "<아래 명령>"
python -I D:/Develop/UBTS/steering-sim-20261108/tools/docker_budget.py release --label <label>
```

컨테이너 안 명령:

```bash
python3 -B -m steering.gz_direct_drive scene --world w0 --out /runs/scene_w0 --views chase,top,front,overhead
python3 -B -m steering.gz_direct_drive check --scene-dir /runs/scene_w0
python3 -B -m steering.gz_direct_drive run --scene-dir /runs/scene_w0 --script w0_turns --out /runs/w0_turns --backend native
python3 -B -m steering.gz_direct_drive scene --world w1 --out /runs/scene_w1 --views chase,top,front
python3 -B -m steering.gz_direct_drive run --scene-dir /runs/scene_w1 --script w1_straight --out /runs/w1_straight --backend native
python3 -B -m steering.gz_direct_drive circles --out /runs/circles --backend native
python3 -B -m steering.gz_direct_drive scene --world w1 --out /runs/scene_w1_rovercam --views ''   # 차량 카메라만
python3 -B -m steering.gz_direct_drive rtf --scene-dir /runs/scene_w1_rovercam --out /runs/rtf --duration 180 --duty 1.0
python3 -B -m steering.gz_direct_drive keyboard --scene-dir /runs/scene_w0      # 터미널(-it)에서
```

- `run`은 `run.json`(설정, 구동기 정보, 프로필 표지, 정지 그림, 영상, 결함 점검, 출처), `log.npz`(물리 주기 기록), `stills/*.png`(글자 있는 것과 `_raw`), `<대본>.mp4`, 궤적 그림을 쓴다.
- `run.json`의 `backend.info`는 `gz_probe.backend_identity()`다: L0는 `info()`, 네이티브는 `result_label()`(빌드 id, 실행 파일 SHA)과 빌드 기록(`build_key`, `binary_sha256`, `source_sha256`, `firmware_build_id`). 처음에는 네이티브 구동기가 `info()`가 없어 클래스 이름만 남았다(리뷰 F2). `provenance.source`는 커밋(컨테이너에서는 호스트가 넘긴 `UBTS_STEER_SOURCE_COMMIT`, `UBTS_STEER_SOURCE_STATUS_SHA256`)과 돈 파일의 SHA 묶음이다. 컨테이너 실행에 두 환경 변수를 넘긴다(`GZ_MODEL_KO.md` 5절).
- 장면 옵션 `--wheel-collision cylinder|sphere`(처음 기본은 cylinder. 2026-11-09 결정 R13-1부터 기본은 sphere, `GZ_MODEL_KO.md` 8절·12절). 3단계부터 정지 그림의 둘째 줄과 그래프 제목에 바퀴 충돌 모양(`바퀴 충돌 구`)을 적고 `run.json`·`circles.json`에 `wheel_collision`을 남긴다.
- 장면 옵션: `--views`(빈 값이면 시연 카메라 없음), `--size`, `--fps`, `--no-rover-camera`, `--front-pivot on|off`, `--suspension on|off`(실험), `--no-wheel-wells`(고치기 전 비교용).
- 키보드 모드는 `gz sim -s -r`(실시간)로 돈다. GUI 클라이언트(`gz sim -g`)를 붙여 볼 수 있다. 시연 카메라는 이 모드에서 첫 자세에 머문다.

## 4. 렌더링 설정과 실측

- GPU 경로를 먼저 시험했고 그대로 동작했다. `compose.ubts.gpu.yaml`과 같은 설정이다: 카메라는 D3D12/Ogre 1(`UBTS_RENDER_ENGINE=ogre`, `UBTS_HEADLESS_RENDERING=0`), `/dev/dxg`, `/usr/lib/wsl/lib`·`/usr/lib/wsl/drivers` 읽기 전용, WSLg X11 소켓. 소프트웨어 렌더링(Mesa llvmpipe, `ogre2` headless)은 시연에서 쓰지 않았다(p5_model A10에서 동작 확인).
- fixture(같은 프로세스) 안에서 Sensors 시스템이 렌더링한다. 프레임에 SIM 시각이 찍힌다. W0 시연(32 s)에서 시연 카메라 4대(1280×720, 30 Hz)와 차량 카메라가 각각 970장을 냈다. 가장 긴 간격은 0.0333 s다(빠진 프레임 0).
- 평균은 30 Hz가 아니라 30.3장/s다. W1 실시간 실행의 프레임 시각을 모두 보면 첫 장 뒤로 25장마다 한 번 간격이 0.025 s(물리 3스텝)이고 나머지는 0.0333 s다. p5_model A10의 30.30 fps도 같은 현상이다. Sensors 시스템의 갱신 시각 계산 때문으로 보이나 조사하지 않았다[추정].
- 렌더링 때문에 fixture 시연은 실시간보다 느리다: SIM/벽시계 W0(카메라 5대) 0.50, W1(카메라 4대) 0.51. 실시간 배율은 5.2절.
- 정지 그림: 1280×720 PNG. 글자 있는 것과 없는 것(`_raw`)을 둘 다 남긴다. 영상: 960×540, 30 fps, H.264(libx264, crf 23), 오른쪽 아래 작은 화면 352×198.
- 그림 위 글자 세 줄: ① 관절 직접 조종 시연 · 안전 사슬 없음 · 평가에 쓰지 않음 ② SIM 자리값(프로필 id) · 월드 · 시점 ③ SIM 시각, 조향 목표(등가), 두 조향 관절 각, duty, 속도. GNSS 좌표는 없다(국소 SIM 좌표만).

- W1 180 s 실행에서 차는 곧게 x 107 m까지 갔다. 열(x 0~30 m)과 끝 길(x 32~36 m)을 SIM 약 50 s에 지나고, 그 뒤는 나무 없는 땅이다. 같은 기록에서 열 안 구간(SIM 20~48 s, x 11.6~34.1 m)만 보면 RTF 0.9993, 카메라 30.30장/s다.

## 6. 찾은 결함과 고친 것

### 6.1 차체 상자와 바퀴가 겹침 → 바퀴 홈 (고침)

- 점검: `gz_model.wheel_body_clearance()`. 바퀴 충돌 원통의 표면 점(둘레 96 × 폭 9 + 양쪽 덮개)과 base_link 충돌 상자 사이의 정확한 상자 거리를 조향 범위 전체(1° 간격)에서 잰다. 음수는 겹친 깊이다.
- 고치기 전(생성된 상자 1.10 × 0.54 × 0.24 m, 바닥 높이 0.20 m): 뒷바퀴 위쪽이 상자 안으로 5.0 cm, 조향한 앞바퀴(±28°)는 7.0 cm 들어갔다. 바퀴 꼭대기 높이는 0.28 m다.
- 한 모델 안 링크끼리는 부딪히지 않는다(`self_collide` false). 그래서 물리 결과는 같았고, 화면에서 바퀴가 차체를 뚫었다. 고치기 전 추격 시점 그림(`p5demo_14`)에서 뒷바퀴 위쪽이 차체 상자 안으로 들어가 보인다.
- 고침: 같은 외형을 위 판과 아래 조각 4개로 나눴다(`gz_model.body_boxes()`). 아래 조각은 바퀴가 조향·피벗 범위에서 쓸고 가는 자리에서 1 cm(`body_wheel_clearance_m`) 떨어진다. 질량·관성·무게중심은 전체 상자 값 그대로다.
- 고친 뒤: 최소 틈 0.0093 m(앞바퀴, 28°, 피벗 끝), 뒷바퀴 0.010 m. axle_pivot 형식, 반경 0.16 m 바퀴, 한계 35°에서도 겹침 0(단위 시험).

### 6.2 W1 출발 때 0.15 m 떨어짐 (고침)

- 원본 과수원 생성기는 자기 차(PX4) 자세를 지형 위 약 0.15 m에 둔다. 조향 차 원점은 바퀴 바닥이라 출발 때 0.15 m 떨어졌다(생성 자세 z 0.099 m, 그 자리 지형 −0.051 m).
- 고침: `gz_assemble.fix_spawn_height()`가 지형 높이 + 0.03 m로 놓는다(`W1_SPAWN_DROP_M`, SIM_ASSUMED). 장면 manifest `world_summary.spawn_height`에 남는다.

### 6.3 W1에서 바퀴가 뜨고 멈춤 → 앞차축 롤 피벗 (고침, 기본 켬)

- 점검 방법: 힘 모드 DC 직선에서 땅에서 힘을 받지 않는 바퀴는 무부하 속도 d·ω0 − f/p로 돈다(시정수 J/p 약 0.06 s). 한 바퀴가 그 속도의 0.03 rad/s 안이고 다른 구동 바퀴가 0.1 rad/s 넘게 느리면(짐을 짐) 그 바퀴를 "뜬 바퀴"로 센다(`run.json` `analysis.unloaded_wheels`). W0 평지 정속에서는 모든 바퀴가 무부하 속도라서 이 조건으로 거른다.
- 고치기 전(단단한 차체): `w1_straight` 대본에서 바퀴 하나 이상이 뜬 시간 비율은 duty 0.48: 86 %, 0.8: 66 %, 1.0: 63 %였다. duty 0.48은 0.4 m 가고 섰다(오른쪽 뒷바퀴가 처음부터 무부하 속도 2.89 rad/s). duty 0.8은 x 3.3 m에서 대각 두 바퀴(왼앞·오른뒤)가 5.03 rad/s로 헛돌며 섰다. p5_model이 본 "W1에서 0.43 m 가고 멈춤"의 원인이다. 토크만의 문제가 아니었다.
- W1 지형: 1~3 m 요철(진폭 0.045 m), 잔 요철 0.01 m, 경사 1.2 %. 바퀴 네 개 높이가 한 평면에 놓이지 않아 단단한 차체는 세 바퀴로 선다.
- 고침: 앞차축 롤 피벗(`front_axle_roll_joint`, 축 x, ±8°, 감쇠 2 N·m·s/rad, 스프링 없음). 세 점 지지가 되어 네 바퀴가 짐을 나눈다. 실제 차의 차체 유연성을 모르므로 SIM_ASSUMED 대용이다.
- 고친 뒤: 뜬 바퀴 비율 0.1~0.5 %(duty 0.48·0.8·1.0 확인 실행). duty 0.48로 44 s에 12 m, 0.8로 24 m, 1.0으로 33 m(열 끝)까지 갔다. 최종 시연 실행(`media_runs2`)에서는 W1 0.08 %, W0 0.07 %다.
- 시험하고 채택하지 않은 방법: 바퀴마다 수직 스프링·감쇠(옵션 `suspension`, 기본 끔). 뜬 바퀴는 0 %가 되었지만 평지 정지 높이가 1.85 cm 낮았다. 작은 실험으로 확인했다(`runs/wf2b/p5_demo/exp2/`).
  - 매단 10 kg: 평형 위치가 이론값과 같다(스프링 기준 위치도 적용됨).
  - 땅 위 네 다리 25.57 kg: 정적 처짐이 하중/k의 2.23배(감쇠 163 N·s/m, 120 Hz). 감쇠 0이면 1.22배, 240 Hz 1.56배, 1 ms 1.12배, k 4배 2.88배.
  - 결론: 이 DART 설정의 관절 스프링은 지면 접촉 아래에서 정적 하중을 틀리게 낸다(스텝이 클수록, 감쇠·강성이 클수록 크다). 평가 모델에 쓰지 않는다.

### 6.4 이상이 없음을 확인한 것

- 회전 방향: 왼쪽 조향(+)이면 위에서 볼 때 반시계(요레이트 +)다. W0 시연의 정상 회전 표본 1118개 모두 부호가 맞았다(곡률 비 중앙값 0.966 = 측정 요레이트/속도 ÷ tan δ/L). 위에서 본 그림·고정 머리 위 그림·고정 조향 원 그림에서도 +에서 왼쪽으로 돈다.
- 관절 떨림: 일정 목표 구간에서 조향 관절 각 표준편차 1.3e-11° 이하, 관절 − 보낸 목표 p99 9.5e-10°(W0)·3.5e-10°(W1), 최대 2.0e-9°. 조향 관절 속도 최대 0.59 rad/s(W0)·0.52 rad/s(W1), 모두 목표가 바뀔 때다.
- W0 바퀴 뜸: 바퀴 중심 높이 − 반경이 −0.63~0 mm(접촉 침투), 2 mm 넘는 표본 0.
- W0 정지 미끄럼: −15°로 조향한 채 선 4 s 동안 위치·yaw 변화 0.

### 6.5 남은 문제 (고치지 않음)

- W1 경사에서 정지 뒤 굴러감: duty 0(release, EN 켬)이면 DC 직선은 속도에 비례하는 제동 토크만 낸다. 쿨롱 마찰(바퀴당 0.077 N·m)은 경사 약 0.4°까지만 붙잡는다. 경사 1~2°에서 0.05~0.2 m/s로 굴렀다(4 s에 0.07~0.6 m). 실제 기어 마찰·정지 유지 값이 없다. 정지 마찰이나 유지 브레이크를 프로필 값으로 정해야 한다(제안 결정).
- 회전 중 속도 손실이 F-SIM 범위보다 크다(p5_model 보고). 피벗 뒤에도 0.3 m/s에서 5/10/20°에 11.0/24.3/56.6 %(전 11.9/26.1/59.6 %), 30 kg 모델에서 10.3/22.7/52.5 %다. 큰 몫은 바퀴 충돌 원통의 양 끝 두 점 접촉이라는 단순화에서 온다(구 충돌이면 1.3/5.0/18.7 %, `GZ_MODEL_KO.md` 8절, 결정 제안).
- release 정지 거리 0.943 m(30 kg 모델, 고친 정지 거리 정의; 목표 0.476~0.690 m 밖). p5_model과 같은 자리값 τ_stall 문제다.
- 위에서 본 시점에서는 차체 판이 바퀴 대부분을 덮는다. 바퀴는 차체 옆으로 나온 부분(뒷바퀴 약 6 cm, 15° 조향한 앞바퀴 약 9 cm)만 보인다. 조향은 앞쪽 시점에서 가장 잘 보인다.
- 차량 자체 카메라(위치 (0.40, 0, 0.48) m, 수평으로 봄, SIM_ASSUMED)는 바로 앞 차체 윗면(높이 0.44 m, 앞끝 0.55 m)이 그림 아래 58줄(360줄 중 16 %, 약 1/6)을 가린다. 앞끝이 카메라보다 0.15 m 앞, 0.04 m 아래라서 계산값(302번째 줄부터)과 같다. 고치기 전 상자도 윗면 높이·앞끝이 같아 같았다. 카메라는 위치 추정에 쓰지 않지만 P6b 대시보드 표시에는 보인다. 실제 카메라 장착 위치·차체 모양을 재면 다시 본다.
- 네이티브 L1 구동기 모델(test_servo)은 주행 중 목표보다 약 1.5° 덜 돈 자리에서 선다(+15° 목표에 등가 13.5°, 바퀴 14.0°/13.1°; +5° 목표에 3.5°). 자리값 백래시 2°와 서보 데드밴드 0.5° 때문으로 본다[추정]. Gazebo 관절은 모델 각을 그대로 따른다(A25). 고정 조향 원 그림은 L0(목표에 정확히 섬)와 L1 두 가지로 남겼다.
- 렌더링 서버를 품은 fixture를 지울 때 SIM 컨테이너에서 프로세스가 메시지 없이 끝났다(처음 실행에서 그림 파일이 안 생김). `run` 명령은 그림까지 쓴 뒤 `os._exit`로 끝낸다. 원인은 찾지 않았다.

## 8. 시험하지 않은 것

- 키보드 모드를 실제 터미널(TTY)에서 손으로 친 것. 파이프로 넣은 키 줄로만 돌렸다(5.3절).
- 소프트웨어 렌더링(llvmpipe)으로 시연 그림 만들기. 시연은 GPU(D3D12) 경로만 썼다. p5_model이 A10에서 소프트웨어 경로를 확인했다.
- 시연 장면에서 Embree LiDAR(`cpu_lidar.py`), ROS 브리지, 대시보드. P6a·P6b 범위다. 시연 카메라 모델은 정적이고 시각 요소가 없어 `mesh_raycast`가 읽어도 걸리지 않을 것으로 보지만 돌려 보지 않았다.
- 서버(실시간) 모드에서 시연 카메라 따라가기. 서버 모드에서는 첫 자세에 머문다.
- 앞차축 롤 피벗의 한계·감쇠 스윕, `axle_pivot` 형식과 피벗을 함께 쓴 Gazebo 실행, 지형 조건(`terrain_ruts` 등).
- firmware 모드 구동기로 조향 관절 몰기(시연에서는 하지 않았다. 측정 probe의 보고는 `GZ_MODEL_KO.md` 12.6절).
- 실차. 모든 값은 자리값이다.

## 9. 통합 담당에게 넘기는 결정 (제안)

- 바퀴 충돌을 구로 바꿀지(`GZ_MODEL_KO.md` 8절, 리뷰 F1). 바꾸면 시연 그림·영상도 다시 만든다.
- 앞차축 롤 피벗을 G-SIM 기본으로 둘지. 이번에 기본으로 켰다(끄기: `front_axle_pivot=False`). W0 합격 검사 판정과 수치는 같고, W1에서 바퀴 뜸과 멈춤이 없어졌다. 실제 차체 유연성은 모른다. 사양 요청서에 "차체·차축이 비틀림을 얼마나 받아 주는가(네 바퀴가 울퉁불퉁한 땅에 다 닿는가)"를 더하면 좋다.
- 정지 유지: duty 0에서 경사 1~2°면 차가 굴렀다. 실제 기어 마찰·정지 유지 힘을 프로필 값으로 정할지(예: 정지 마찰 토크, 또는 brake 모드의 유지 토크).
- 바퀴 홈 차체: 실제 차체 모양(바퀴 홈, 바닥 높이 `ground_clearance_m` 0.10 m와 G-SIM 0.20 m의 차이)을 실측하면 바꾼다.
- 카메라 장/s: 30 Hz로 둔 카메라가 gz Sensors에서 30.30장/s(25장마다 한 번 0.025 s 간격)로 나온다(4절). 카메라 장/s 판정과 대시보드 표시에서 이 값을 30 Hz 설정의 정상 값으로 볼지, 원인을 조사할지.
- 차량 카메라 위치: 차체 윗면이 그림 아래 16 %를 가린다(6.5절). 실측 전까지 그대로 둘지. 사양 요청서에 카메라 장착 높이·앞쪽 차체 모양을 더하면 좋다.
- 평가 실행에는 시연 카메라를 넣지 않는다는 규칙을 둘지. 1280×720 두 대를 더하면 W1 RTF p10이 0.88로 떨어졌다(5.2절). W1에서 실시간 배율을 다시 잴 때는 열 안에서 끝나게 길이를 정할지(duty 1.0이면 약 50 s에 열을 지난다).
- 이미지: 이 브랜치의 새 이미지 ID 두 개를 이미 썼다. 이번 소스(시연 모듈, 모델 고침, 리뷰 고침)는 이미지에 없다. 다음 이미지 빌드 때 들어간다(`docker/Dockerfile.ubts-steer`의 import 검사에 `gz_direct_drive`를 더했고, 펌웨어 소스 복사와 `firmware_build_id` 검사를 더했다, 리뷰 F8).
- 바퀴 뜸 분석의 문턱(무부하 속도 0.03 rad/s, 다른 바퀴 0.1 rad/s)은 τ_stall 1.6에 맞춘 속도 문턱이다. v0.1(p 0.657)에서는 뜨지 않은 바퀴도 걸린다(10절). 토크 기준(예: 바퀴 토크 < 일정 N·m)으로 다시 정할지.
