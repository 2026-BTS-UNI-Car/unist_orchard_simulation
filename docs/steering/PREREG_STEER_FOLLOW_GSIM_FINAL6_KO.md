## 0. 바뀐 것과 까닭

Windows 호스트 CPU 는 평균 43~49 %, 봉우리 74~88 % 였고 RTF 는 0.87 위여서 RTF 규칙(0.5 미만)에 걸리지 않았다.

6단계 1단계 개발 확인(판정 아님, 기록 폴더 `runs/gsim_stage6_20261114/`):

- Windows 프로세스별 표본기(1 s)를 A 꼴 1 run(wf8, 통과)과 F 꼴 1 run(사용자 명령, 2.6 m 에서 `stale_lidar` 뒤 STOP) 동안 돌렸다. 전체
  CPU 는 스택 없음 16 %, 우리 스택이 쉴 때 37~47 %, A run 평균 40 %(p90 56, 최대 71), F 실패 직전 5 s 평균 54 %(최대 71.5)였다. 표본기가
  늦은 표본은 없었다. 우리 스택(vmmemWSL) 밖의 몫은 화면 합성(dwm) 약 0.9 코어, 원격 화면 프로그램 약 0.8 코어, svchost, 보안 프로그램
  0.2~1.5 코어, 작업 창(VS Code) 0.2~2.9 코어였다. F 실패 전 1.5 s 동안 실행기의 스캔 처리(55 -> 276 ms)·조향 상태 갱신·브리지 왕복이
  함께 3~10 배 느려졌다(VM 전체가 느려진 꼴). 논리 CPU 별로 보면 이 PC 는 P 코어 12 개(등급 1)와 E 코어 10 개(등급 0)이고, 전원 구성
  '균형 조정'에서 일이 P 코어에 몰리고 E 코어가 0 % 인 때가 있었다. 왜 전체 70 % 남짓에서 그렇게 느려지는지는 가르지 못했다.
- 쉬는 실행기(py-spy, 스레드별 CPU): run 전 22.0 %(ROS 입력 스레드 13.9 %: rclpy 실행기가 약 164 콜백/s 마다 노드의 서비스 7 개를 대기
  집합에 넣는다, 주 스레드 5.2 %: SIM 시계 2 ms 폴링, GIL 탐침 0.4 %), run 이 끝난 뒤 58.1 %(ENDED 에서도 추정기가 스캔을 처리한다: 정지
  관측, 실차 코드의 뜻이라 그대로).

실행기 쪽 바꿈(`a4f60c1`, 실행기가 정하는 것은 그대로):

## 1. 공통

5단계 등록 1절 그대로(SIM 시계, 세션마다 새 스택, healthy 뒤 120 s, 판정 단계 5 s 창 RTF 0.5 미만은 호스트 고장으로 다시, 부하 확인
기록, 사용자 스택은 내리고 무거운 잠금). 이미지는 `ubts-steer-sim:wf9`(이 등록을 넣은 커밋의 깨끗한 작업 트리에서 등록 run 전에 빌드,
매니페스트 = 커밋 blob, compose 기본 태그). 더하는 것:

- **호스트 표본기**: 모든 세션 동안 Windows 프로세스별 표본기(1 s: `GetSystemTimes`의 전체 CPU, 표본기 늦음, 상위 프로세스, 논리 CPU 별
  사용률)를 돌린다. docker stats 는 15 s 마다(5단계 5 s), Windows CPU 를 따로 읽는 두 번째 프로세스는 없앤다.
- **측정 스택 포트**: A·B 의 측정 스택은 대시보드를 `127.0.0.1:18091`에 연다(기록 폴더의 compose override, `ports: !override`). 18090 을
  연 채 둔 호스트 브라우저 탭이 측정 스택에 붙지 않게 한다(5단계 B 의 다른 세션). F 는 사용자 명령 그대로 18090 이다.
- **(i) 호스트 조용함 사전 확인**: 판정하는 run 바로 전에(A: 120 s 기다린 뒤 follow 검사 전, B: 기다린 뒤 브라우저 대본 전, F: 매
  `sim_auto.py start` 전) 표본기의 마지막 **30 s** Windows 전체 CPU 평균이 **45 % 미만**이어야 한다. **5 s** 마다 보고 **최대 900 s(15 분)**
  기다린다. 기다린 시간과 평균을 적는다. 900 s 가 지나도 아니면 그대로 시작하고 그렇다고 적는다.
  - 까닭(1단계): 스택 없는 호스트 16 % + 쉬는 우리 스택(vmmemWSL 약 3.1 코어 = 14 %)이 30 % 남짓이고, 쉬는 스택에서 잰 평균은 A 37 %,
    F 47 %(작업 창 출력 포함)였다. 45 % 는 다른 호스트 일에 약 2.6 코어를 남기고, F 실패 직전 5 s 평균 54 %보다 낮다.
- **(ii) 넓힌 호스트 고장 규칙**: 실패한 run(A, F)이나 실패한 세션(B)은, 표본기에 그 **실패 사건 전 5 s** 안에 Windows 전체 CPU 가
  **70 % 이상**인 표본이나 제때보다 **1.0 s 이상** 늦은 표본(표본 간격 >= 1 s + 1.0 s)이 있을 때만 호스트 고장(무효, 세지 않음)으로 적는다.
  - 실패 사건: A·F 는 go 뒤 처음으로 상태가 ACTIVE 가 아닌 실행기 틱의 벽시계(`diag.ww`), run 이 열 끝(`row_end`)으로 끝나지 않았을 때만.
    B 는 등록 항목에 속한 검사 중 처음 실패한 것의 벽시계(대본이 검사마다 적는다). 열 끝까지 갔지만 기준을 못 맞춘 run 은 호스트 고장
    시험 없이 실패다.
  - 시계: 실행기 벽시계는 세션마다 잰 차이(`docker exec`의 `time.time()`을 두 번의 호스트 읽기 사이에 다섯 번, 왕복이 가장 짧은 것)를
    빼서 Windows 시각으로 바꾼다.
  - 무효인 자리는 사전 확인 뒤 **최대 두 번** 다시 돈다(A·B: 새 스택, F: 같은 스택에서 `sim_auto.py start`와 `reset` 한 번 더). 시도는 모두
    적는다. 세 번 다 무효인 자리는 판정하지 않는다. 호스트 고장이 아닌 실패는 실패로 센다. RTF 규칙은 그대로다.
  - 까닭: 5단계 실패의 봉우리는 74~88 % 이거나 표본이 2.2 s 끊겼다. 1단계에서 통과한 A run 의 1 s 표본 106 개 중 70 % 이상은 1 개였다
    (실패가 우연히 5 s 창에 걸릴 확률 약 5 %). F 실패 직전 5 s 최대는 71.5 % 였다.
- run 마다 적는 것: 사전 확인(기다림, 평균), run 동안의 표본기(평균, p90, 최대, 가장 큰 늦음, 가장 높은 표본의 상위 프로세스), 실행기
  스캔 처리 p50/p99/최대(ACTIVE 틱의 `proc_ms`), 루프 p50/p99/최대와 건너뛴 틱, 에뮬레이터 `clock_stalls`, A 의 `discovery_settle`,
  실패한 run 의 실패 사건과 호스트 고장 시험.

## 2. A: 열 추종 4 run (W1, SIM 시계)

- 5단계 A 와 같다(`exec_checks follow`, `nominal_1`, `nominal_2`, `nominal_3`, `lateral_p040`, run 마다 새 스택, `steer_follow_gsim_v1`
  한도, 검사는 Start 전에 DDS 가 조용해질 때까지 기다린다).
- 통과 = 판정된 run 이 모두 통과, 네 자리 중 셋 이상 판정.
- 원인 규칙(판정과 별개, 미리 정함, 판정은 기록대로): 실패 사건이 ESP 에뮬레이터의 0.25 s 넘는 /clock 정지가 끝난 뒤 1.0 s 안(단조 시각)에
  있으면 SIM 쪽(스택의 DDS 전달), 아니면 실행기·제어기 쪽. 실행기 입력 진단이 기본 꺼져 있어 에뮬레이터 기록만 본다. 호스트 고장 시험은
  따로 적는다.

## 3. B: SIM 대시보드 화면 (6 항목 전부)

## 4. F: 사용자 명령 그대로 3 run (회귀)

- 저장소 밖 로컬 도구 폴더 `tools/local_env/`에서 `python -B sim_stack.py start --no-browser`(기본 이미지 wf9, 기본 SIM 시계), 150 s 뒤
  `python -B sim_auto.py start`, 끝나면 `python -B sim_auto.py reset`, 20 s. 세 자리. 매 start 전 1절 (i), 무효 자리는 1절 (ii).
- `sim_stack.py`는 `main` 가지의 compose 파일을 내보내 쓴다(`--ref` 기본값). 이 가지가 병합되기 전이라 그 파일에는 실행기 CPU 가중치와
  `UBTS_STEER_EXEC_INPUT_DIAG`가 없다(이미지 기본값 = 진단 끔). 실행기 바꿈은 이미지 wf9 에 들어 있다.
- 통과 = 판정된 세 run 모두 실행기 run_end 의 end_reason `row_end`. 무효로 남은 자리가 있으면 F 는 판정하지 않는다.
